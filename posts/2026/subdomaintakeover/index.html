What is Subdomain takeover


Subdomain Takeover is a type of cyberattack in which a hacker takes over a company's subdomain. This can happen if there is a DNS record that is pointing to a third-party service (such as Amazon Web Services or GitHub) that has either been deleted, abandoned, deprovisioned or abandoned., this will result in what is known as a "dangling" CNAME record

DNS records and third-party platforms are stored separately. This means if you delete a service from a third-party platform, your DNS record will remain unchanged. Therefore, an attacker can then register that unused subdomain with the third-party platform, and because your DNS record is pointing to that same subdomain, any traffic sent to it will be secretly directed to the same subdomain.

Attack Lifecycle


In a professional red teaming or bug bounty scenario, a security researcher can typically do the following steps to indentify and exploit the dangling records

subdomain Recon

First, we need to map the target's surface to identify many subdomains as possible. Security researchers often utilizes tools C99 Subdomain Finder to discover valid subdomains and filter for the not resolved to an active IP ones.

Fingerprinting & CNAME Analysis

Once you have your subdomains list, it's time to analyze the DNS architecture. Check for a CNAME footprint pointing to cloud providers. While this can be done manually using commands as dig, we can also automatizate this process using high-concurrency tools like Subjack

Executing the Takeover

If a vulnerability is confirmed, we can log into the respective cloud provider platform (e.g., AWS, Github, Heroku) and deploy a new project with the exact identifier specified in the target's dangling CNAME record. Doing all this, we can take full control of the subdomain.

Proof of Concept (PoC) Laboratory

Testing this vulnerability in live production can be really dangerous and unethical. To safely visualize of this mechanism, we can build a local enviroment using Docker containers. You can download the complete lab in this repository: https://github.com/j4f3th/Subdomain-Takeover-Demo

Phase 1: Deploying the Architecture

We spin up our local infrastructure, we will get up a custom DNS server and a legitimate third-party application service in HTTP

Next, we inspect the DNS records for our target app.company.local

bash 

dig @172.20.0.2 app.company.local

The query confirms that our target points to a third-party service via a CNAME record, If we send a HTTP request with curl, we can observe the normal behavior of the application:

bash 

curl -s -H "Host: app.company.local" http://172.20.0.3 | html2text
Note

html2text is a command-line command that strips the HTML tags to clean raw text in the terminal.

Mitigations and Preventative Strategies

Remediating subdomain takeovers requires a good synchronization between asset lifecycle managements and DNS administrations, Organization should improve the following aspects:


1. Strict De-provisioning Workflows:Enforce a strict "DNS-First" decommisioning policy before any cloud bucked, web app, external service is deleted from a provider.

2. Dynamic Network Assignment:Avoid hardcoded configurations for dynamic microservices. Instead. leverage internal proxy headers, use a managed API gateways, or a dynamic service mesh registries to route traffic.

3. Automated Asset Auditing:Implement in your infrastructure a continuous routine scan which check the organization's inventory for dangling CNAME records, when anomalies occur like an external cloud enpoint returning 404 error, the scanner will warn you and your organization.

Conclusion

Subdomain takeovers represent a critical flaw born from broken asset lifecycles rather than complex software bugs. The danger is amplified because the malicious content is recieved from a trusted domain name, While the exploit mechanism is straightfoward, mainteining a healthy visibility and automated auditing over your external DNS recors is the best way to eliminate the risk.
